# 01 — 需求规格与设计决策（ADR）

## 1. 需求规格

### 1.1 核心需求（六大项）

**R1 海底环境模拟与实时调节**
- 模拟海底水流环境：流速、流向、光线、能见度/浊度、水温、湍流强度。
- 以上参数在训练过程中通过环境控制面板**实时调整**，立即生效（物理与渲染同步响应）。
- 环境变化应产生可感知的物理影响（流速增大 → ROV 漂移/姿态扰动增强）。

**R2 作业模拟环境**
- 至少包含 4 个场景：水下打捞（Underwater Salvage）、大坝检测（Dam Inspection）、船舶检测（Ship Inspection）、桥梁检测（Bridge Inspection）。
- 场景通过**注册表机制**扩展，后期新增场景不改动核心代码。

**R3 视角系统**
- 三种视角可切换：第三视角（Chase/Orbit）、第一视角（POV/驾驶舱）、声纳视角（Sonar）。
- 第三视角支持 **Blender 风格**鼠标操作：**鼠标中键拖动旋转视角**（围绕 ROV 公转）、滚轮缩放、可平移。
- 快捷键或 UI 按钮切换视角。

**R4 ROV 机型选择与配置**
- 进入训练前可选择 ROV 机型；不同机型主要差异为**可用自由度数量**（第一版提供 6 自由度通用机型，配置系统为后续机型预留）。
- 支持补光灯开关切换（灯光数量/功率由机型配置决定）。

**R5 第一视角 HUD（POV 参数显示）**
- POV 中必须显示：机身姿态模型（迷你 3D 姿态指示器）、罗盘（航向）、俯仰角、机身速度（节）、横滚角、当前深度、当前温度。

**R6 ROV 控制能力**
- 补光灯开关控制。
- 航速调节，**最大 4.5 节**（≈2.315 m/s），可通过面板/滑块调节目标航速上限。
- **一键恢复水平姿态**（自动姿态稳定到 roll≈0、pitch≈0，不改变深度与航向）。

### 1.2 约束

- 网页端运行（现代浏览器，WebGL2 支持），纯前端静态部署，无后端。
- 第一版 ROV 模型**代码生成**（几何体组合），后续提供 GLTF 模型文件支持不同机型外观。
- 培训用途：操作手感真实度优先于物理绝对精度。

### 1.3 非目标（第一版不做）

- 多人联机、教练远程监控（后续版本）。
- 手柄支持（架构预留 Gamepad API 映射位，第一版不做）。
- 教学分步关卡（第一版不做引导系统）。
- 真实流体 CFD 仿真（简化水动力模型即可）。

## 2. 架构决策记录（ADR）

> 每条 ADR 记录"背景 → 决策 → 后果"。后续开发若推翻某条 ADR，必须新增 ADR 说明原因。

### ADR-001 技术栈：Three.js + React + TypeScript
- **背景**：需要 WebGL 3D、复杂 UI 面板、长期可维护性。
- **决策**：Three.js（命令式渲染层）+ React 18 + TS + Zustand + Vite。
- **后果**：UI 与渲染解耦；渲染层以封装类形式暴露，React 组件不直接持 Three.js 对象；仿真循环在 React 之外运行，通过 Zustand store 桥接。

### ADR-002 渲染层命令式而非 react-three-fiber
- **背景**：物理/渲染循环需要精确控制，React 的渲染周期不适宜直接驱动高频循环。
- **决策**：Three.js 命令式封装（`Engine`/`SceneManager` 类），React 只管 UI；通过 store 与事件通信。
- **后果**：代码更直白、易调试、性能可预期；代价是少量样板代码（初始化/销毁/同步逻辑）。

### ADR-003 简化水动力模型（推力 + 浮力 + 阻尼 + 水流）
- **背景**：培训目标是操作手感，不需要 CFD 级精度；需稳定 60FPS。
- **决策**：六自由度刚体动力学，力源 = 推进器推力 + 重力 + 浮力（含浮心恢复力矩）+ 非线性阻尼 + 水流拖曳 + 湍流扰动。忽略附加质量/科氏耦合（可后续通过系数近似）。
- **后果**：实现简单、调参直观；在 4.5 节低速工况下手感足够真实。

### ADR-004 固定步长物理积分（1/120s）
- **背景**：数值稳定性和可复现性是培训模拟器的硬要求。
- **决策**：物理循环固定步长 `dt = 1/120`，内部累积剩余时间，多步追赶；渲染循环独立于物理。
- **后果**：低刷新率（30Hz）下物理仍然稳定；物理步长恒定保证操控一致性。

### ADR-005 键盘 + 鼠标控制（第一版）
- **背景**：学员设备不确定性大，手柄普及率低。
- **决策**：键盘映射六自由度指令 + 鼠标（左键交互 UI、中键拖第三视角）；输入层做成可映射表结构，为手柄预留接口。
- **后果**：`InputMapper` 抽象层，`KeyMapping` 可配置（未来可存 localStorage）。

### ADR-006 场景/机型/任务全部注册表化
- **背景**：需求明确"后期会添加场景与机型"，必须低耦合扩展。
- **决策**：定义 `SceneDefinition` / `ROVConfig` / `TaskDefinition` 接口 + 注册表（Registry），核心引擎只认接口。
- **后果**：新增场景 = 新增一个注册文件，不改核心代码。

### ADR-007 声纳视角采用 2D 扇形 FLS 模拟
- **背景**：真实 ROV 培训需要识别前视声纳（Forward-Looking Sonar）图像的能力。
- **决策**：在场景中按声纳射线采样生成距离数据，叠加噪声/衰减/多径伪影，渲染成 2D 扇形灰度图。
- **后果**：视觉真实感强、教学价值高；对场景几何有采样成本，需限制每帧射线数与更新频率。

### ADR-008 纯前端部署 + localStorage 持久化
- **背景**：第一版无后端，快速落地。
- **决策**：Vite 静态构建，设置/成绩存 localStorage，成绩支持 JSON 导出。
- **后果**：零运维；跨设备不共享数据（后续加后端时数据层可替换）。

### ADR-009 姿态欧拉角约定：Three.js `YXZ` 顺序
- **背景**：ROV 姿态显示（roll/pitch/yaw）与 Three.js 旋转顺序必须唯一映射，避免 AI 开发时混乱。
- **决策**：ROV `Object3D.rotation.order = 'YXZ'`，即 `rotation.x = pitch`、`rotation.y = yaw`、`rotation.z = roll`；模型前向 = `-Z`（Three.js 惯例）。
- **后果**：与相机第三人称跟随姿态一致；HUD 数值直接读欧拉角，无需额外转换（详见 `03-物理仿真.md` 坐标系章节）。
